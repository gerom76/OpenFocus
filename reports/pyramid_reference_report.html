The pyramid against the render it was tuned on

Helicon Focus method C is a Laplacian pyramid — the same algorithm as this one — and it ships here at four smoothing settings on the same photographed stack. HF-C-1, its lightest smoothing and so the sharpest render it offers, is the reference the 1.44.0 tuning was scored against. The third column is a setting that won every other measurement the project owns and was rejected here; it is on the page because that is what this page is for.

Three settings, one reference

All three are the current code run three times; only the two named dials differ. 1.44 is what ships: the base band moved 3 → 8. Rejected also took selectivity 8 → 16, which gains 0.5–1.1 dB on every fixture that has a ground truth and wins on every subsampled reading of this capture.

Why the third column lost. It recovers 1.233 of the reference's tile contrast against 1.108, past the 1.20 this method is held to on the full stack — and the extra is not detail. The zone split below is what shows that, and two numbers in this table already hint at it: flat-field noise 1.728 → 2.022, and the pooled distance from the reference getting worse, 0.673 → 0.710, while tile agreement improves. Agreement says where the detail is and cannot tell texture from grain; that is what the zones are for.

The same window, 1:1

Helicon's render is warped onto our grid by a similarity fit — scale, rotation, translation — so all four show the same content. The residual drift after that fit is real: focus breathing is a different magnification per frame, so no single warp removes it, which is why every number on this page is pooled over tiles or zones rather than taken per pixel.

Read the rejected row against the one above it: selectivity 16 gains +0.25 in the quietest zone and +0.04 in the busiest. It is amplifying what the reference found nothing in about 6 times as hard as what it found the most in. That is the whole argument for leaving the default where it is.

And a gap none of these settings closes. Every column stands around 3.8× the reference in the quietest zone and about 0.78× in the busiest — grainier than Helicon where neither resolves anything, and slightly softer where the detail actually is. That is a property of the method rather than of this tuning, nothing in the suite currently holds it, and it is the more interesting result on this page.

Inside Helicon's own smoothing range

Four settings of one algorithm bracket where a single render can only score. Recovering less contrast than method C at its lightest smoothing means this method has gone soft; more than at its heaviest means it has gone crunchy; between them is the range a mature implementation of this algorithm considers reasonable.

This measure rises with frame count — the shipped default reads 0.916 of HF-C-1 over 28 frames and 1.108 over all 333 — so the bound quoted here is the full-stack one, and a setting chosen on a subsample means nothing until it has been re-measured at this density. That is the trap the rejected column fell into, and confirm_at_full_density in tests/fusion_autotune.py now closes it: the tuning loop re-measures its winner on every frame before it may write to source. test_the_whole_capture_fuses in tests/test_pyramid_electronics_ant.py asserts the same bound.
