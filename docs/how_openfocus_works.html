The render pipeline

Every stage below is optional except loading and export. A run can be fusion only, registration only, or both; the same pipeline serves the interactive window and the batch worker, so a batch job reproduces exactly what the main window is set to.

1 · IMPORT
source
A folder of numbered frames, individual files, a video, or a drag-and-drop onto the window, the executable or the dock. Images JPG PNG BMP TIFF WebP; JXL with imagecodecs; RAW NEF NRW DNG with rawpy; video MP4 AVI MOV MKV WMV FLV WebM, decoded into frames.
2 · LOAD
decode & normalise
Frames decode in parallel across cores. JPEG can decode on the GPU via nvJPEG; RAW is developed by LibRaw; JPEG XL gets the whole machine, split between decode workers and libjxl's own pool. The stack is sized before it is read, so the thread count is bounded by free memory. Optional downsample on the way in — by percentage or by target long edge.
3 · REGISTER
optional
Scale → Homography → ECC, independent stages that run in pipeline order. Each measures its transform, all of them compose, and the frames are resampled once onto a single shared canvas — one Lanczos4 warp, one crop. Anchored to a selectable reference frame.
4 · REGION
optional
Full frame, or a selected region of interest. Crop saves the region alone; Paste fuses the region and blends it back onto a chosen base frame.
5 · FUSE
the core
One of eight algorithms decides, per pixel or per band, which frames carry the detail. Frames wider than the tile threshold are processed in overlapping tiles so memory stays bounded; five of the eight methods have a GPU path with automatic CPU fallback.
6 · REFINE
optional
IFCNN passes the fused result and the original stack through a convolutional fusion network to recover detail the blending stage missed. Needs PyTorch and the IFCNN checkpoint on disk.
7 · ENHANCE
optional · non-destructive
Auto (colour-safe global tone curve) or Local (CLAHE), with a strength slider. Applied when the result is previewed and when it is saved — never to the stored render, so it can be changed or removed without fusing again.
8 · EXPORT
result
A single image, the aligned stack as a folder or GIF, or a drag straight out of the app. The source frame's EXIF is carried across and an XMP packet records the version, render date, duration and every option the render used — spliced in without recompressing the pixels.

Entry points: File → Open Folder (Ctrl+O) · Open Video (Ctrl+Shift+O) · drag onto the window · drag onto the executable, Dock or .desktop launcher · command-line arguments.

The loading engine

  • Parallel decode. Frames load across CPU cores rather than one at a time — roughly 4× on RAW and large stacks.
  • GPU decode. JPEG can be decoded on the GPU through nvJPEG, and RAW developed there too. Toggled under Settings → GPU Image Loading. JPEG XL has no GPU path and cannot have one — no GPU JXL decoder exists.
  • Sized before read. RAW and JXL stacks are measured from their headers first, so the app can state the memory the stack will occupy, warn when it is too much, and bound the worker count accordingly.
  • Interruptible. A load reports progress and stops at its next checkpoint when asked.

Downsample on import

A dialog appears on every folder open, offering two ways to shrink the stack:

Scale factorA percentage applied to every frame
Long edgeA target in pixels for the longer edge, applied per image — so a mixed-size stack ends on one common long edge

Frames already at or below the target are left alone. Downsampling never enlarges.

Bit depth

Set under Settings → Bit Depth. The chosen depth holds from load through alignment and fusion to export.

AutoFollows the source — engages 16-bit whenever any frame carries more than 8 bits default
8-bitForces the narrow path; smallest memory footprint
16-bitForces full depth even from 8-bit sources, leaving headroom for blending

A 16-bit run means no banding in smooth gradients and no quantisation loss where frames are averaged together.

Labels & annotation

Text labels can be overlaid on the input stack and on the registered stack independently, and removed from either. Overlay colours are authored in 8-bit units and scaled to the working depth, so a label looks the same at either depth.

Viewing & navigation

Source frames above, result below, with a draggable splitter. Navigating the source panel moves the result panel to the matching frame where one exists.

Inspection

Mouse-wheel zoom, Ctrl+wheel for fine steps, double-click to toggle fit / 100 %, click-drag to pan, and a press-and-hold magnifier for pixel-level checks.

Frame selection

Tick frames in the source list to render a subset — every n-th frame, or an arbitrary selection. The saved metadata records "k of n frames" when a subset was used.

Registration

Correcting the geometry between frames before they are blended. Three independent stages, one resample.

The three stages, in pipeline order

StageWhat it correctsHow it fitsWhen to reach for it
Scale off by default The magnification change a lens introduces as the focus plane moves through the stack — focus breathing A constrained similarity — uniform scale, rotation, translation — via estimateAffinePartial2D with RANSAC on keypoint matches When the subject visibly grows or shrinks between the first and last shot. Cancels size drift without the overfitting a full homography risks on blurred frames
Homography Global perspective change and larger geometric shifts SIFT/ORB keypoints and RANSAC. Fits both a perspective transform and a constrained similarity per pair, and keeps the perspective one only where it predicts matches it was not fitted to Handheld captures, or scenes with real perspective change. The model gate means a stack shot on a rail is not bent to fit feature-matching noise
ECC Residual sub-pixel misalignment Intensity-based optimisation maximising the enhanced correlation coefficient — no features required Subtle drift, and as a finishing pass after Homography. Slower but more precise; low-texture frames it can still handle where feature matching cannot

Stages are independent checkboxes. Any combination is valid, and when several are on they always run Scale → Homography → ECC regardless of the order you tick them.

Why one warp matters

Each stage measures its own transform on downsampled frames, but the transforms are composed into a single matrix per frame before any pixel moves. The stack is then resampled once, with Lanczos4, onto one shared canvas and cropped once to the region every frame covers. A three-stage pipeline that resampled per stage would interpolate three times — softening the frame — and crop three times, throwing away roughly a further tenth of it.

Reference frame

Transforms are measured between neighbours and chained back to one fixed frame. Alignment error accumulates with distance from that anchor, so which frame anchors the chain decides where the residual drift ends up. The reference is only cropped, never warped.

First — default, error grows toward the endframe 1 → n
Middle — halves the longest chain, drift spread symmetricallyframe 1 → n
Last — the mirror of Firstframe 1 → n
Anchor — held fixed
Accumulated chain distance (bar height)

Choose Middle for long stacks where the far end drifts or ghosts; Last when the most important detail sits at the end of the stack.

When registration is worth running

  • Frames were captured handheld, or the rig moved
  • The subject changes size across the stack — enable Scale
  • The scene has parallax, so nearer objects shift between frames
  • Results show ghosting or doubling — almost always a registration problem, not a fusion one

If registration fails

Try one stage at a time, lower the downscale width, and check the frames have enough contrast and texture for features to be found. Single-channel (greyscale) stacks are handled by all three stages.

Fusion algorithms

Eight ways to decide which frame owns which detail. All eight take the same stack and produce one all-in-focus render.
Guided Filter GPU
Spatial domain · edge-preserving weight maps · Li, Kang & Hu 2013
Builds a per-frame weight map from local saliency and refines it with a guided filter, so weights follow real edges instead of blurring across them. Fast, balanced, and forgiving — the historical default.
Kernel3–51 px, odd · default 31
SpeedFast
QualityGood
DCT GPU
Frequency domain · block-wise · Haghighat et al. 2011
Measures each block's detail energy in the DCT domain and picks the frame that holds it. The focal-plane map is median-filtered to remove isolated blocks, and neighbouring frames are blended across the block lattice so the grid does not show.
Kernel3–151 px · default 31 (filters the block map, not pixels)
Block4 · 8 · 16 · 32 px · default 8
PlateauCrisp · Balanced · Smooth
BlendOn / off across the lattice
SpeedMedium
QualityGood
DTCWT GPU
Dual-tree complex wavelets · multi-scale, multi-directional · Lewis et al. 2007
Decomposes each frame into shift-invariant complex wavelet subbands at several scales and six orientations, fuses the coefficients by activity, and reconstructs. Strong on scenes with detail at many different scales.
KernelNot used — the decomposition sets the scale
Needsdtcwt; GPU path via pytorch_wavelets
SpeedMedium
QualityVery good
GFG-FGF GPU
Gradient focus measure + fast guided filter · Fu et al. 2024
A generalized four-neighbourhood Gaussian gradient operator scores focus, and a fast guided filter refines the resulting weight maps. Cheap to compute and decisive where focus regions are clearly separated.
Kernel3–51 px, odd · default 7
SpeedFast
QualityGood
Pyramid recommended default GPU
Laplacian pyramid, weighted rather than choose-max · after Burt & Adelson 1983
Each frame is split into band-pass detail levels plus a smooth base. Every detail band becomes a weighted mean across the stack, each frame weighted by how far its pooled local energy falls behind the best on offer — a frame twice behind the winner contributes well under a percent, so a genuine focus decision is still a decision, while frames that tie (a background no frame resolves) are averaged instead of picked between. Energies are compared in units of each frame's own grain, so a bright noisy frame cannot win the areas holding no detail. The base band follows the frames that won the detail. Collapsing the pyramid reconstructs the image, and every pixel is finally held inside the range its own frames span, so bands taken from different frames cannot add up to a value no frame had.
Six controls, all exposed and all defaulted to their measured best — see page 5. The textbook choose-max rule remains available as Selectivity → Winner takes all.
KernelEnergy pooling window · default 5 px (small by design — the pyramid pools again at every level)
SpeedFast
QualityVery good
Depth Map — Max CPU only
Per-pixel select from a local Laplacian focus measure
Each pixel is taken whole from the frame whose focus measure is highest there — the classic hard depth map, and an order-independent argmax. Colour and noise never blend across a slice boundary. The family behind Zerene DMap and Helicon methods A/B.
KernelFocus-measure window · default 9 px
HaloSuppression radius in px · 0 = off
SpeedFast
QualityVery good
Depth Map — Average CPU only
Contrast-weighted blend from the same focus measure
Frames are blended in proportion to their focus measure, with a small baseline weight. A flat region — where every frame is equally defocused — collapses to the plain mean and recovers the stack's multi-frame SNR, a free √N noise reduction, while textured regions still follow the frame that holds the detail.
KernelFocus-measure window · default 9 px
HaloSuppression radius in px · 0 = off
SpeedFast
QualityGood
StackMFF-V4 needs PyTorch
Pretrained deep model · the AI path
A neural network trained on large multi-focus datasets learns the fusion rule rather than being given one. Highest quality of the eight when the hardware is there. It runs on CUDA or Apple MPS and falls back to CPU automatically; on a card that runs out of memory, the inference batch halves itself and retries, and the size it actually ran at is written into the result's metadata. Inputs are resized to a multiple of 32 for the network's pooling depth, and a preview too small to pool is refused with an explanation rather than producing something wrong.
Batch1–16 tiles per inference · default 2, halves itself under VRAM pressure
KernelNot used — the network decides

Refinement, compute & tuning

Every control here is a trade rather than a right answer — which is why it is exposed. The defaults are what measured best on the project's test stacks.

+ IFCNN refinement — a stage, not a method

A separate checkbox that runs after whichever method you chose. The fused result and the original stack go through a fully convolutional fusion network that recovers detail the blending stage missed. It refines a fused image, so it cannot run on its own; it needs PyTorch and the IFCNN checkpoint on disk, and the checkbox greys out with the expected path in its tooltip when either is missing. Results are labelled <method> + IFCNN.

Compute paths

GPU work goes through PyTorch — CUDA on NVIDIA, MPS on Apple Silicon. Every GPU path falls back to CPU automatically if the device, the library or the memory is not there, and says so in the status console. The status bar shows CUDA, MPS, N/A or Err; Help → Environment Info reports what was actually detected.

GPU: Guided FilterGPU: DCTGPU: DTCWT GPU: GFG-FGFGPU: PyramidGPU: StackMFF-V4 GPU: IFCNNCPU only: Depth Map

Pyramid — the six controls

ControlOptionsDefaultWhat it does
Kernel slider3–51 px, odd5 The window each band's focus energy is pooled over before frames are compared. Small follows fine detail and can chase grain; large decides region by region and rounds off narrow in-focus structures. Small by design — the pyramid pools again at every level, so this window covers twice as much picture at each one
Pyramid levelsAuto, 2–8Auto How many band-pass levels each frame is split into. Auto is five, clamped to what the image size can carry. Fewer decide focus on coarser structure; more separate scales finely and cost time
SelectivityAverage · Soft · Balanced · Strict · Winner takes allBalanced How sharply each band favours the sharpest frame. Balanced and Strict let a genuinely sharp frame win outright while frames that tie are averaged. Average and Soft blend more of the stack in — smoother backgrounds, softer detail. Winner takes all is the textbook choose-max rule: it takes the single best coefficient everywhere, including in defocused areas where "best" is decided by grain
Scale coherenceOff · Light · Medium · StrongOff Makes the coarse levels guide the fine ones, so a pixel cannot take its fine detail from one frame and its coarse structure from another. Reach for it when detail looks like it is sitting on the wrong background. Off by default because it costs sharpness where near meets far
Base bandMean · Gentle · Balanced · StrongBalanced How hard the smooth low-frequency layer follows the frames that won the detail bands. Mean averages every frame and hazes the result when most of the stack is defocused; Strong follows the sharp frames hardest
Ignore grain when nothing is sharpOn / OffOn Compares frames in units of their own noise, so a bright, grainy, completely defocused frame cannot win the areas where nothing is in focus and stamp its flat tone over them
Keep pixels within the source rangeOn / OffOn Holds every pixel between the darkest and brightest value its own frames actually have there. Rebuilding an image from bands taken out of different frames can otherwise produce values no frame had

If a smooth, defocused area comes out crossed by thin dark strokes

The two switches at the bottom of the list are what remove them, and both are on by default — check they have not been turned off. Keep Selectivity at Balanced or lower rather than Winner takes all. If the strokes survive that, try Scale coherence at Light or Medium.

DCT — the three controls

ControlDefaultEffect
Block size8 pxThe grid every DCT decision is made over — 4, 8, 16 or 32. Smaller follows fine detail and is noisier; larger is steadier but steps harder where near meets far
PlateauBalancedHow far below the peak energy a frame still counts as in focus on a block. Crisp (0.85) keeps a never-sharp background closer to its sharpest frame; Smooth (0.70) averages more frames there, coming out flatter. Presets rather than a slider — above 0.85 detail-free regions go back to being decided by grain
BlendOnBlends neighbouring frames across the block lattice. Turning it off copies each block verbatim from a single frame — true source pixels, at the cost of the lattice showing again

DCT's kernel slider median-filters the focal-plane map, which holds one entry per block rather than per pixel — so each step reaches eight times further than it does for the pixel-domain methods. That is why its ceiling is 151 rather than 51.

Depth Map — halo suppression

A defocused foreground edge casts a bright glow over the background in exactly the frames where that background is sharp. Plain per-pixel selection copies the glow straight into the result — the classic focus-stacking halo.

With a radius set, a sharply focused region also claims the surrounding band its glow contaminates, so the ring comes out as natural defocused background instead.

Radius 0Off — bit-identical to not passing the option at all
Set it toRoughly the visible halo width, in pixels
CostLarger values round off genuine detail near depth edges — the same trade the Radius dial has in Helicon Focus and Zerene Stacker

Use the smallest value that clears the glow. Both Max and Average accept it; Average halos less to begin with, because its blend weights spread.

Kernel, tone & memory

The one slider shared across the methods, the enhancement applied after fusion, and how large stacks are kept inside available memory.

Kernel size at a glance

DTCWT · StackMFF-V4——Not used by these methods

Values are always odd. Broadly: smaller keeps local detail and more noise; larger is smoother and better at suppressing noise.

Contrast enhancement

A post-fusion stage, off by default. It is applied when the result is displayed and again when it is saved — never to the stored render — so it previews live and can be changed or removed without fusing again.

AutoA colour-safe global tone curve. Brightness moves through a luminance gain, so hue is untouched
LocalCLAHE — contrast limited adaptive histogram equalisation, working region by region
Strength0–100 %. At 0, or with the method off, the input is returned unchanged

Depth-aware: a 16-bit result stays real 16-bit data, not 8-bit values widened into a bigger type. The setting in force at save time is what gets written into the result's metadata.

Tuning is recorded, not lost

Any control moved off its default is written into the output filename, so two renders that differ only in tuning cannot overwrite each other — and the full set lands in the file's XMP either way. Batch jobs inherit whatever the main window is set to.

Tiling — the memory strategy

Large frames are fused in overlapping tiles rather than whole, because GPU memory demand scales with tile area and with the square of the stack size. The overlap is what keeps the seams invisible.

SettingDefaultRangeEffect
Block size1024 px64 – 16384Smaller = less memory, slower
Overlap256 pxup to 4096Raise it if seams show
Threshold2048 px256 – 131072Frame size above which tiling engages at all

How many tiles run at once is derived from free memory at render time, not from the thread count — and forced to one for the GPU methods, which are already parallel inside a tile. A render that tiled records both facts in its metadata.

Performance settings

SettingDefaultWhat it controls

Out of memory?

Enable or tighten tiling, reduce the block size, use a smaller kernel, or downsample the stack on import. For CUDA specifically, lower the StackMFF batch size — though it already halves itself and retries on an allocator failure.

Working modes, batch & output

What a single run can be asked to do, how to queue many of them, and the nine ways a result leaves the application.

Three ways to run a job

Registration and fusion are independent selections, so a run is whichever of them you tick:

Fusion onlyNo registration stage selected. The frames are taken as they are — correct for a stack shot on a rigid rail or a microscope stage
Registration onlyNo fusion method selected. The output is the aligned stack, savable as a folder or a GIF. Recorded in metadata as "None (registration only)"
BothThe frames are aligned, then fused. The aligned stack is cached and reused if you re-render with the same registration settings, so only the fusion runs again

Changing any registration setting invalidates that cache — the alignment is only reused on an exact match of stages and reference frame.

Region of interest

Fuse a part of the frame instead of all of it — much faster when you are comparing settings, and the only way to treat one subject differently from its surroundings.

1 · EnableThe ROI button. Needs at least two frames loaded; the stack is aligned with ECC first, automatically, so the region means the same thing in every frame
2 · DrawDrag a rectangle on the result panel
3 · RenderA dialog asks how to output it
CropThe result is a small image containing only the selected region
OverlayThe result is a full-size image — a chosen base frame with the fused region pasted onto it

Batch processing

Queue any number of folders and leave it running. Each folder is processed independently, with live progress and cancellation at any point.

SettingsInherited from the main window — the same fusion method, kernel, tuning, registration stages, contrast, bit depth and tiling
OutputInto a subfolder of each input, alongside the input, or into one custom folder
FormatChosen per batch from the same list as the save dialogs; the choice is remembered
NamingTimestamp plus the parameters that were used, so runs never collide

Dropping several folders onto the window asks whether they are one stack or many, and routes to batch when they are many.

Ways out of the app

  • Save result (Ctrl+S) — one fused image, format from the dialog
  • Save stack (Ctrl+Shift+S) — the registered or the input stack, as a folder of images or as an animated GIF
  • Drag out — drag a result from the output list straight into another application
  • Batch output — written automatically, one result per input folder

Interrupting a render

The Stop button activates for the duration of a render. It unwinds at the next safe checkpoint — between pipeline stages, or between tiles on large images — the controls unlock and no result is produced. On a heavily tiled image this takes a moment while tiles already in flight finish.

DNG, metadata & quick reference

What the raw-converter path does, what a saved file remembers about its own render, and where to look when something is wrong.

DNG output settings

An uncompressed linear (already demosaiced) DNG at full 16-bit, tagged with an already-neutral white balance and the transfer curve the develop actually applies — so Lightroom or RawTherapee renders the result you saw, not a second tone curve on top of it. Reloading one into OpenFocus returns the exact pixels.

CompressionNone (default) · Lossless Huffman JPEG — identical pixels at about half the size · Lossy baseline JPEG with a quality setting, 8-bit only, meant for proxies
Fast-load previewEmbeds a half-resolution JPEG in a SubIFD, so browsers and raw converters draw a thumbnail from a few hundred kilobytes instead of decoding the full linear raw
Colour spacesRGB primaries, or the source camera's own colorimetry where the file can supply it

The lossless mode is only offered where imagecodecs can read it back — a result that cannot be reopened is not a result. Make and Model stay OpenFocus's own, because those are what a converter reads to pick a camera profile.

What a saved result remembers

Two metadata groups are written into every JPG, PNG and JXL result, without recompressing the image:

EXIFThe block from the first source frame of the render — camera, lens and exposure survive the stack
XMP · CameraEvery camera tag of the source, cloned as plain text, so the shot's settings read without an EXIF parser
XMP · OpenFocusProgram version, render date, render duration, and every option the render ran with

The OpenFocus group is written from one shared vocabulary, so two files are directly comparable. It records: source frame count (and whether a subset), registration stages and reference frame, downscale width, fusion method, kernel and halo size, the full pyramid tuning, StackMFF batch size, IFCNN, contrast, region, tiling and tile workers, bit depth, processing unit and thread count. A stage that did not run says so rather than being absent — enough to reproduce the render months later.
